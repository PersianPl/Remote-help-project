# Remote Help — Protocol v1

نسخه پروتکل: `1` (بخش ۳۶ معماری). این سند **قرارداد مشترک بین Backend و هر دو کلاینت** است.

---

## ۱. اصل کلی: پروتکل از لایه انتقال مستقل است (بخش ۳۵)

پیام‌های زیر را می‌توان از سه مسیر جابه‌جا کرد:

```text
SignalingTransport (interface سمت کلاینت)
    ├── WebSocket      ← VPS (آینده)
    ├── SSE            ← هاست اشتراکی (اختیاری)
    └── Long-Polling   ← هاست اشتراکی (پیاده‌سازی فعلی: server/)
```

contract سمت کلاینت (پسودوکد):

```text
interface SignalingTransport {
    connect(baseUrl, token)
    send(name, payload)          // POST /api/signal
    onMessage(callback)          // حلقه: GET /api/signal?since=lastId
    close()
}
```

تغییر transport در آینده = تعویض پیاده‌سازی، **نه** تغییر پیام‌ها.

## ۲. REST Endpoints

همه پاسخ‌ها JSON هستند. احراز هویت با `Authorization: Bearer <token>`.

| متد و مسیر | نقش | توضیح |
|---|---|---|
| `GET /api/v1/health` | همه | سلامت + وضعیت DB؛ `?hold=N` تست Long-Polling |
| `POST /api/v1/sessions` | — | ساخت جلسه → `{session_id, code, host_token, ...}` |
| `GET /api/v1/sessions/{id}` | host/viewer | وضعیت جلسه؛ `{id}` = session_id یا human code |
| `POST /api/v1/sessions/{id}/join` | — | ورود بیننده با کد → `{viewer_token, ...}` (یک‌بارمصرف) |
| `POST /api/v1/sessions/{id}/approve` | host | تأیید بیننده |
| `POST /api/v1/sessions/{id}/reject` | host | رد بیننده → closed |
| `POST /api/v1/sessions/{id}/close` | host/viewer | قطع جلسه (idempotent) |
| `GET /api/v1/signal?since=N&hold=S` | participant | دریافت پیام‌ها؛ حداکثر `max_hold` ثانیه نگه داشته می‌شود |
| `POST /api/v1/signal` | participant | ارسال `{v?, name, payload}` پس از approve |

> مسیر کاننیکال `/api/v1/...` است؛ نسخه بدون `/v1` (`/api/...`) به‌عنوان alias سازگار حفظ شده است.
> روی جلسه‌ای که به `closed`/`expired` رسیده، poll فوراً برمی‌گردد (hold نمی‌شود).

## ۳. نام پیام‌های Signal

### از طرف کلاینت‌ها — Matrix نقش‌ها (مرحله ۶)

| name | payload | نقش مجاز | شرط state |
|---|---|---|---|
| `offer` | `{sdp}` | **فقط host** (مالک استریم صفحه) | approved → negotiating |
| `answer` | `{sdp}` | **فقط viewer** | approved/negotiating/connected |
| `ice` | `{candidate, ...}` | هر دو نقش | approved/negotiating/connected |
| `status` | `{state:"connected"}` | هر دو نقش | negotiating → connected |

- نقض matrix → `403 role_not_allowed` (جلوی answer جعلی توسط viewer را می‌گیرد).
- فیلد `v` (اختیاری در v1): اگر ارسال شود باید عدد `1` باشد، وگرنه `400 unsupported_protocol_version`.
- `payload` باید JSON object باشد؛ آرایه → `400 invalid_payload`.

### از طرف سرور (`sender = system`)

| name | معنا |
|---|---|
| `session.join_requested` | بیننده درخواست داده؛ host باید approve کند |
| `session.approved` | درخواست تأیید شد؛ نوبت Signaling/WebRTC |
| `session.closed` | جلسه بسته شد (`payload.reason`: rejected/closed) |
| `session.expired` | انقضای کد یا TTL جلسه |

## ۴. چرخه پیام Signal (Long-Polling)

```text
1. GET  /api/v1/signal?since=<lastSeenId>&hold=20   ← نگه داشته می‌شود
2. سرور هر ~۳۰۰ms صف را چک می‌کند؛ پیام جدید → همان لحظه پاسخ
3. پاسخ: {messages:[{id,sender,name,payload,ts}...], state, now}
4. کلاینت آخرین id دیده‌شده را نگه می‌دارد و دوباره وصل می‌شود
5. POST /api/v1/signal {v?:1, name, payload} → 201 {id}
```

`id` سراسری و صعودی است؛ فیلتر `session_id` سمت سرور انجام می‌شود.
مرجع JSON: `shared/protocol/v1.schema.json`.

## ۵. State Machine (بخش ۳۷ + جدول سخت‌گیرانه مرحله ۵)

```text
waiting ──join──► join_requested ──approve──► approved ──offer──► negotiating ──status──► connected
   │                    │                        │                                      │
   │ close/expire       │ reject/close/expire     │ close/expire                         │ close/expire
   ▼                    ▼                         ▼                                      ▼
 closed/expired       closed/expired            closed/expired                        closed/expired
```

انتقال‌های مجاز — **فقط این‌ها** (منبع حقیقت: `SessionState::ALLOWED`):

| از | به |
|---|---|
| `waiting` | `join_requested`, `closed`, `expired` |
| `join_requested` | `approved`, `closed`, `expired` |
| `approved` | `negotiating`, `closed`, `expired` |
| `negotiating` | `connected`, `closed`, `expired` |
| `connected` | `closed`, `expired` |
| `closed` / `expired` | — (نهایی؛ از هیچ مسیری برنمی‌گردند) |

- هر انتقال خارج از جدول سمت سرور رد می‌شود (`InvalidTransitionException` → `409`).
- stateهای نمونه `REJECTED` / `FAILED` / `CLOSING` به‌صورت `closed` + `payload.reason` جمع شده‌اند.
- Signaling فقط از `approved` به بعد مجاز است.
- `expired` با lazy check روی هر درخواست اعمال می‌شود (بدون دیمون).

## ۶. کدهای خطای API

`{"error": {"code": "...", "message": "...", ...}}`

| HTTP | code | معنا |
|---|---|---|
| 400 | `invalid_code` / `invalid_json` / `unknown_signal_name` / `unsupported_protocol_version` / `invalid_payload` | ورودی نامعتبر |
| 401 | `missing_token` / `invalid_token` | توکن نیست/نامعتبر |
| 403 | `forbidden` (نقش) / `session_mismatch` (توکن متعلق به جلسه دیگر) / `role_not_allowed` (matrix سیگنال) | مجوز ندارد |
| 404 | `unknown_session` / `not_found` | جلسه یا مسیر ناموجود |
| 409 | `already_joined` / `not_joinable` / `invalid_state` / `state_not_allowed` / `session_closed` | تعارض وضعیت |
| 410 | `session_expired` | منقضی شده |
| 413 | `payload_too_large` | بدنه بزرگ‌تر از حد |
| 429 | `rate_limited` (+`retry_after`) | محدودیت نرخ (بخش ۵۰) |
| 500 | `internal_error` | خطای داخلی (جزئیات فقط در log سرور) |

## ۷. STUN/TURN در config کلاینت

از روز اول آدرس‌ها **در config** باشند نه در کد (بخش 67.4):

```json
{
  "protocol_version": 1,
  "signaling": { "transport": "long_polling", "base_url": "https://api.example.ir" },
  "ice": { "stun_urls": [], "turn": [] }
}
```

روی هاست اشتراکی هر دو لیست خالی می‌مانند تا Decision Gate (افزودن coturn یا VPS).
